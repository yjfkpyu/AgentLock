# doc ↔ code 反查映射

> 本表用于回答："我刚改了 `src/foo/**`，需要同步哪些文档？"
>
> 数据来源是各正式文档 front-matter 中的 `code_owns` 字段。建议在 CI 或 AI 收口时由脚本扫描所有 `docs/**/*.md` 与根入口文件后再生本表，避免手工维护漂移。
>
> 字段约定与 front-matter 规则见 [`../08-process/conventions.md`](../08-process/conventions.md) §4 §6。

## 使用规则

- 改代码时优先查本表反查权威文档；若代码路径未在表中，按 [`../../DOCS_MAINTENANCE.md`](../../DOCS_MAINTENANCE.md) §10.1 判断是否需要新增 `code_owns` 声明。
- 一条代码路径可能被多份文档共同声明；这种情况通常意味着权威边界尚未收敛，应在 [`../../SESSION.md`](../../SESSION.md) 的 Known Drift 中记录，再在对应文档里收敛。
- 出现“代码已存在但无任何文档声明”时，说明文档覆盖有缺口；应在 [`feature-registry.md`](feature-registry.md) 或 backlog 中补齐。

## 反查表

| 代码路径（glob） | 权威文档 | 关联功能 | 备注 |
|-----------------|----------|---------|------|
| `src/<待填写>/**` | [`../<待填写>.md`](../README.md) | F-xxx | 待填写 |

## 未覆盖代码区登记

> 用于显性化“尚无任何文档声明权威”的代码路径，避免长期沉默漂移。

| 代码路径 | 发现日期 | 处理方式 | 状态 |
|---------|---------|---------|------|
| 待填写 | YYYY-MM-DD | 新建文档 / 扩展现有文档 / 显式不归属 | open |

## 维护规则

- 新增 / 删除 / 重命名正式文档时，同步检查 `code_owns` 与本表。
- 当 `code_owns` 由脚本生成时，本文应只保留人工补充列（例如“备注”“处理方式”）；自动列由脚本覆写。
- 本文状态升级为 Current 之前，应已存在可运行的扫描脚本或显式手工维护承诺。

## 自动生成区段建议

当项目实现自动扫描脚本时，建议把脚本输出包裹在以下标记之间，方便重复覆写而不破坏人工维护内容：

```markdown
<!-- AUTO:doc-code-map start -->
| 代码路径（glob） | 权威文档 | 关联功能 | owner |
|-----------------|----------|---------|-------|
| ... | ... | ... | ... |
<!-- AUTO:doc-code-map end -->
```

## 项目接入脚本指引

模板不内置具体的反查表生成脚本，因为生成方式与项目技术栈强相关（Node / Python / Go / Rust / Shell 各不相同）。

真实项目接入时，AI 应先确认：

1. 项目主语言与包管理器（决定脚本运行时与依赖管理）
2. 是否已有 CI / pre-commit 框架（决定脚本注册位置）
3. 是否需要将自动列写回本文件（决定输出方式）

然后参考 [`../../scripts/README.md`](../../scripts/README.md) “项目接入时的脚本扩展指南”实现脚本。
