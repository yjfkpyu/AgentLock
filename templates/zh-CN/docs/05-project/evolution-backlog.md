# 进化清单

> 承接当前阶段不做、但未来可能需要转正的能力、设计点、约束或工程化要求。
>
> 相关入口：[../../AGENTS.md](../../AGENTS.md) · [../../SESSION.md](../../SESSION.md) · [feature-registry.md](feature-registry.md)
>
> 状态、Track、转正流程统一见 [../08-process/conventions.md](../08-process/conventions.md)。

---

## 1. 用途

本文件用于承接“现在不做，但未来可能重要”的设计点，避免两类问题：

- 当前阶段文档被远期设想塞满，导致实现范围变重、AI 判断失焦。
- 远期关键考虑完全丢失，项目从原型、试点、早期版本或内部工具进化到更真实的使用环境时没有回看依据。

本文件不是 issue tracker，也不是详细设计文档。它只记录：**设计点存在、为什么未来可能需要、何时触发、会阻塞什么**。

## 2. 使用规则

1. 如果某个设计点不阻塞当前阶段验收，默认先进入本文件，而不是写进当前权威设计正文。
2. 如果正式文档必须提到该远期目标，只写简短说明并链接到本文件对应条目，不展开细节。
3. 每条条目必须写清触发条件；没有触发条件的条目通常只是愿望，不应升级为正式设计。
4. 条目一旦触发，应升级到对应正式文档（PRD、架构、API、数据模型、测试策略等），并同步更新 feature-registry 的 `Track`。

## 3. 状态约定

| 状态 | 含义 |
|------|------|
| backlog | 已登记，未启动 |
| triggered | 触发条件满足，可启动正式设计 |
| in-design | 已升级为正式设计文档 |
| obsolete | 经评估不再需要 |

## 4. 条目模板

复制以下模板新增条目：

```md
### E-001 <标题>

- **类别**：<产品 / 架构 / 数据 / 性能 / 安全 / 运维 / 体验 / 组织流程 / 其他>
- **当前阶段现状**：<现在怎么处理，或为什么不做>
- **未来目标**：<未来要达到什么能力或约束>
- **触发条件**：<什么事实发生后才启动，例如第 2 个客户、第 2 个场景、真实数据接入、性能压力出现>
- **阻塞影响**：<不做会阻塞什么，或带来什么风险>
- **来源讨论**：<来源文档 / 会议 / 用户决策 / 代码证据>
- **相关文档**：<链接到相关正式文档或计划>
- **相关功能**：<F-xxx 或 none>
- **状态**：backlog
```

## 6. 毕业条件

当项目出现以下情况时，应回看本文件，把满足触发条件的条目升级为正式设计：

| 触发节点 | 应做动作 |
|----------|----------|
| 当前阶段核心验收通过 | 检查 `BOTH` 条目是否需要扩展 |
| 新阶段启动 | 检查 `LATER` 条目是否应转为 `NOW` 或 `BOTH` |
| 新客户 / 新用户群 / 新部署环境出现 | 检查安全、权限、性能、运维、数据隔离相关条目 |
| 第 2 个相似场景出现 | 检查是否需要抽象通用模型或共享组件 |
| 线上问题或用户反馈反复出现 | 检查是否有对应 backlog 条目应升级 |

毕业流程：

1. 将条目状态改为 `triggered`，记录触发证据。
2. 将条目升级到对应正式文档，补齐接口、数据、验收或工程规则。
3. 同步更新 [feature-registry.md](feature-registry.md) 的 `Track`、阶段和状态。
4. 如果条目已经被正式文档吸收，把状态改为 `in-design`；如果确认不再需要，改为 `obsolete`。
