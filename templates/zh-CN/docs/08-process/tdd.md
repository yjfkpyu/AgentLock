# TDD 建议

> 本文档定义测试驱动开发建议。核心逻辑、协议、安全、权限、数据迁移和高风险变更应优先采用 TDD；文档、小样式、小配置或探索性改动可使用轻量验证。

## 核心规则

1. **先红后绿**：适合 TDD 的任务，先写一个会失败的测试，再写让它通过的最小实现
2. **不假装 TDD**：如果没有先写红测，收口时说明采用的是事后测试或轻量验证
3. **测试即文档**：测试用例描述应说明预期行为，而非重复实现细节

## 最小 TDD 循环

```
红测 → 最小实现 → 绿测 → 重构 → 回归
```

1. 写失败的测试（红）
2. 写通过测试的最小代码（绿）
3. 重构实现，保持测试绿色
4. 跑受影响的回归测试

## 高风险任务建议强制测试

- 对外 API、事件协议、CLI、IPC 或设备接口
- 数据模型、迁移脚本、权限、安全、审计、租户隔离
- 复杂业务规则、核心算法、不可逆操作
- 历史上反复回归的问题

## 测试层次

| 层次 | 范围 | 运行频率 |
|------|------|---------|
| 单元测试 | 单个函数/类 | 每次实现变更 |
| 集成测试 | 模块间交互 | 每个任务 |
| 回归测试 | 受影响范围 | 每个任务完成前 |
| 全量回归 | 整个测试套件 | 每个里程碑 |

## 与 superpowers 的关系

若已安装 `test-driven-development` skill，该 skill 提供更详细的 TDD 执行步骤和质量门禁。本文档定义项目级的 TDD 标准，skill 作为增强执行器。
